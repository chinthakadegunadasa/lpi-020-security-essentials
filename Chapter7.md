## 7.1 Linux Network Security & Packet Filtering Frameworks
Linux network security is anchored within the **Netfilter** kernel framework, which intercepts, inspects, and modifies network packets moving through system network interfaces.
```
+-----------------------------------------------------------------------------------+
|                            NETFILTER PACKET FLOW                                  |
+-----------------------------------------------------------------------------------+

                          [ Packet Ingress ]
                                  |
                                  v
                         +-----------------+
                         |   PREROUTING    |
                         +--------+--------+
                                  |
                        /-------------------\
                       /  Routing Decision   \
                       \  Is Packet Local?   /
                        \-------------------/
                          /               \
                   YES   /                 \  NO (Forwarding)
                        v                   v
               +-----------------+  +-----------------+
               |     INPUT       |  |     FORWARD     |
               +--------+--------+  +--------+--------+
                        |                   |
                        v                   |
               [ Local Process ]            |
                        |                   |
                        v                   v
               +-----------------+  +-----------------+
               |     OUTPUT      |  |   POSTROUTING   |
               +--------+--------+  +--------+--------+
                        |                   ^
                        \                   /
                         \-----------------/
                                  |
                                  v
                          [ Packet Egress ]

```
### 1. Packet Processing Hooks & Chains
 * **PREROUTING:** Evaluates packets immediately as they arrive at the network interface prior to routing decisions (used for Destination NAT / Port Forwarding).
 * **INPUT:** Evaluates packets destined for processes running on the local host system.
 * **FORWARD:** Evaluates packets routed through the host from one network interface to another (router/gateway mode).
 * **OUTPUT:** Evaluates packets generated by local processes on the host system.
 * **POSTROUTING:** Evaluates packets after routing decisions, just before egress (used for Source NAT / Masquerading).
### 2. Standard Netfilter Tables
 1. **filter:** Default table for general packet filtering (INPUT, FORWARD, OUTPUT).
 2. **nat:** Used to modify packet source or destination addresses (PREROUTING, OUTPUT, POSTROUTING).
 3. **mangle:** Used for specialized packet header alterations (ToS, TTL, marking packets for Quality of Service).
 4. **raw:** Configures exemptions from connection tracking state mechanisms.
### 3. Stateful Packet Inspection (Connection Tracking)
Stateful firewalls maintain the state of network connections in memory using conntrack:
 * **NEW:** Packets initiating a fresh network connection (e.g., incoming TCP SYN).
 * **ESTABLISHED:** Packets belonging to an already negotiated active connection sequence.
 * **RELATED:** Packets initiating a secondary connection linked to an existing active transfer (e.g., FTP data channels or ICMP errors).
 * **INVALID:** Packets that cannot be identified or associated with any known connection state (should be explicitly dropped).
## 7.2 iptables vs. Modern nftables Subsystem
nftables is the modern successor to iptables, providing higher performance, atomic rule updates, simplified syntax, and unified handling of IPv4, IPv6, ARP, and Ethernet bridge filtering.
```
+------------------------------------+------------------------------------+
| iptables                           | nftables                           |
+------------------------------------+------------------------------------+
| Separate utilities (iptables,      | Unified framework (`nft`) handling |
| ip6tables, arptables, ebtables)    | IPv4, IPv6, ARP, and Netdev        |
| Fixed default tables and chains    | User-defined tables and chains     |
| Non-atomic sequential rule evaluation| Atomic rule updates and execution |
| Higher kernel overhead             | Dual-lookup sets and maps performance|
+------------------------------------+------------------------------------+

```
### Key nftables Structural Elements
 * **Tables:** Containers for chains. Specified under families: ip, ip6, inet (dual-stack IPv4/IPv6), arp, bridge, netdev.
 * **Chains:** Groups of rules attached to specific Netfilter hooks (input, output, forward, prerouting, postrouting).
 * **Sets:** High-performance data structures holding IP addresses, subnets, or port numbers for single-rule bulk evaluation.
## 7.3 Intrusion Detection and Automated Banning Systems
Securing network perimeters requires proactive monitoring and automated mitigation against brute-force attacks and unauthorized port scanning.
```
[ Attacker ] ---> (Failed SSH Logins / Port Scan) ---> [ System Logs / Interceptor ]
                                                                |
                                                                v
                                                       [ Fail2ban / AIDE ]
                                                                |
                                                                v
                                                     [ Dynamically Inserts ]
                                                     [ DROP Rule in Firewall]

```
### 1. Fail2ban Automated Banning
 * **Mechanism:** Scans log files (e.g., /var/log/auth.log or systemd journal) for repeated authentication failures using regular expression patterns.
 * **Mitigation:** Dynamically updates nftables or iptables rules to temporarily or permanently block malicious source IP addresses.
 * **Configuration:** Defined in /etc/fail2ban/jail.conf and custom overrides in /etc/fail2ban/jail.local.
### 2. Advanced Intrusion Detection Environment (AIDE)
 * **Mechanism:** A host-based file integrity checker that builds a cryptographic baseline database (hashes, permissions, timestamps, file sizes) of critical system binaries and configuration files (/etc, /usr/bin).
 * **Mitigation:** Periodically audits the active file system against the known-good baseline to detect rootkits, unauthorized file modifications, or malicious drop-ins.

You are a Lead Infrastructure Security Engineer at **Cybergate Services Private Limited**. An enterprise Linux edge relay node has been provisioned with multiple public interfaces. Recent log audits reveal persistent SSH brute-force attacks and unsolicited port probes.
You must implement a default-deny dual-stack stateful firewall using nftables, configure dynamic IP banning for SSH abuse using **Fail2ban**, execute network security scanning and traffic analysis using **tcpdump**, and establish an initial file integrity baseline using **AIDE**.
```
[ Edge Relay Node ]
  ├── Default-Deny Stateful nftables Rule Set
  ├── Dynamic SSH Brute-Force Defense (Fail2ban)
  ├── Host File Integrity Tracking (AIDE)
  └── Packet Analysis Pipeline (tcpdump / tshark)

```
## 7.5 Hands-On Laboratory: Firewalling, Packet Analysis, and HIDS Setup
In this lab, you will configure a stateful nftables firewall, analyze live network packets with tcpdump, configure automated banning using Fail2ban, and run host integrity audits with AIDE.
### Prerequisites
 * A Linux host (Ubuntu/Debian or RHEL family) with root or sudo privileges.
 * Install required packages:
   ```bash
   # Debian / Ubuntu
   sudo apt-get update && sudo apt-get install -y nftables tcpdump tshark fail2ban aide
   
   ```
### Step 1: Building a Stateful Default-Deny Firewall with nftables
 1. Flush any existing legacy or active rules:
   ```bash
   sudo nft flush ruleset
   
   ```
 2. Create a unified IPv4/IPv6 table named filter_table:
   ```bash
   sudo nft add table inet filter_table
   
   ```
 3. Add standard input, forward, and output chains with strict drop policies for incoming traffic:
   ```bash
   sudo nft add chain inet filter_table input '{ type filter hook input priority 0; policy drop; }'
   sudo nft add chain inet filter_table forward '{ type filter hook forward priority 0; policy drop; }'
   sudo nft add chain inet filter_table output '{ type filter hook output priority 0; policy accept; }'
   
   ```
 4. Allow traffic on the local loopback (lo) interface:
   ```bash
   sudo nft add rule inet filter_table input iifname "lo" accept
   
   ```
 5. Permit stateful connections (ESTABLISHED and RELATED):
   ```bash
   sudo nft add rule inet filter_table input ct state established,related accept
   
   ```
 6. Explicitly drop packets in an INVALID connection state:
   ```bash
   sudo nft add rule inet filter_table input ct state invalid drop
   
   ```
 7. Permit incoming SSH (port 22) and HTTPS (port 443) traffic:
   ```bash
   sudo nft add rule inet filter_table input tcp dport { 22, 443 } ct state new accept
   
   ```
 8. Permit limited ICMP echo requests (ping) with rate limiting:
   ```bash
   sudo nft add rule inet filter_table input meta l4proto icmp limit rate 5/second accept
   
   ```
 9. Display and inspect the active nftables ruleset:
   ```bash
   sudo nft list ruleset
   
   ```
 10. Save the active ruleset persistently across reboots:
   ```bash
   sudo nft list ruleset | sudo tee /etc/nftables.conf
   sudo systemctl enable --now nftables
   
   ```
### Step 2: Capturing and Inspecting Network Packets with tcpdump
 1. List available network interfaces on the system:
   ```bash
   ip link show
   
   ```
   *(Identify your main interface name, e.g., eth0, ens3, or enp0s3).*
 2. Capture 5 ICMP packets on your active interface (replace eth0 with your interface name):
   ```bash
   sudo tcpdump -i eth0 -c 5 icmp
   
   ```
   *In another terminal window or host, run ping -c 3 127.0.0.1 or ping your interface IP to trigger captures.*
 3. Capture TCP port 22 traffic, displaying ASCII payload contents and preventing DNS name resolution:
   ```bash
   sudo tcpdump -nn -v -X -i eth0 port 22 -c 3
   
   ```
   * *Flags:* -nn disables host/port resolution for maximum speed; -v enables verbose logging; -X displays hex and ASCII packet contents.
 4. Write raw packet data directly to a .pcap trace file for external analysis:
   ```bash
   sudo tcpdump -i eth0 -w /tmp/traffic_capture.pcap -c 20 port 22 or port 443
   
   ```
 5. Read and analyze the saved .pcap capture file using tshark:
   ```bash
   sudo tshark -r /tmp/traffic_capture.pcap -Y "tcp.port == 22"
   
   ```
### Step 3: Configuring Dynamic IP Banning using Fail2ban
 1. Copy the default jail.conf to create a custom persistent configuration file:
   ```bash
   sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
   
   ```
 2. Create a targeted SSH jail override file /etc/fail2ban/jail.d/sshd.local:
   ```bash
   sudo cat << 'EOF' | sudo tee /etc/fail2ban/jail.d/sshd.local
   [sshd]
   enabled = true
   port = ssh
   filter = sshd
   backend = systemd
   maxretry = 3
   findtime = 600
   bantime = 3600
   banaction = nftables-multiport
   EOF
   
   ```
   * *Configuration parameters:* Triggers a block after 3 failed login attempts within a 600 second window (10 minutes). Bans the offending IP for 3600 seconds (1 hour) using nftables.
 3. Restart and enable the fail2ban service:
   ```bash
   sudo systemctl restart fail2ban
   sudo systemctl enable fail2ban
   
   ```
 4. Check the operational status of the SSH protection jail:
   ```bash
   sudo fail2ban-client status sshd
   
   ```
 5. Simulate testing an IP ban and unban manually using the client utility:
   ```bash
   # Manually ban a test IP address
   sudo fail2ban-client set sshd banip 192.168.100.250
   
   # Verify banned list status
   sudo fail2ban-client status sshd
   
   # Unban the test IP address
   sudo fail2ban-client set sshd unbanip 192.168.100.250
   
   ```
### Step 4: System File Integrity Monitoring with AIDE
 1. Initialize the baseline AIDE database:
   ```bash
   sudo aideinit
   
   ```
   *(This process scans key system binaries and creates a baseline snapshot in /var/lib/aide/aide.db.new.gz).*
 2. Activate the newly generated baseline database:
   ```bash
   sudo cp /var/lib/aide/aide.db.new.gz /var/lib/aide/aide.db.gz
   
   ```
 3. Simulate an unauthorized modification of a monitored system configuration file:
   ```bash
   sudo echo "# Unauthorized system edit" | sudo tee -a /etc/hosts
   
   ```
 4. Run an integrity check against the baseline database to detect unauthorized alterations:
   ```bash
   sudo aide --check
   
   ```
   * **Result:** AIDE reports that /etc/hosts has been modified, highlighting altered checksums, size, and modification timestamps.
### Laboratory Cleanup
Clean up output trace files and revert the modified configuration file:
```bash
sudo sed -i '/# Unauthorized system edit/d' /etc/hosts
rm -f /tmp/traffic_capture.pcap

```

#### Question 1
Which Netfilter packet processing hook evaluates incoming packets immediately upon arrival at a network interface, prior to any local host routing decisions?
 * A) POSTROUTING
 * B) INPUT
 * C) PREROUTING
 * D) FORWARD
#### Question 2
When implementing stateful packet inspection in an nftables or iptables firewall ruleset, which connection state matches packets that belong to an established, active TCP connection stream?
 * A) NEW
 * B) RELATED
 * C) ESTABLISHED
 * D) INVALID
#### Question 3
Which tcpdump command flag prevents DNS resolution of IP addresses and service port numbers, significantly accelerating packet capture performance during active security incidents?
 * A) -vvv
 * B) -nn
 * C) -X
 * D) -w
#### Question 4
How does Fail2ban detect unauthorized SSH login attempts and automatically apply network block rules?
 * A) By intercepting raw SSH packets at the kernel level before decryption occurs.
 * B) By inspecting log files or systemd journals for repeated authentication failure patterns using regex filters.
 * C) By querying external threat intelligence public blocklists over encrypted HTTPS APIs.
 * D) By executing continuous AIDE cryptographic checksum checks on the /etc/passwd file.
### Answers and Explanations
 1. **Correct Answer: C (PREROUTING)**
   * *Explanation:* The PREROUTING hook intercepts packets as soon as they enter the network stack, before the routing subsystem decides whether the packet is intended for the local host (INPUT) or needs to be routed elsewhere (FORWARD).
 2. **Correct Answer: C (ESTABLISHED)**
   * *Explanation:* The ESTABLISHED state matches packets that are part of an already negotiated, bidirectional connection track.
 3. **Correct Answer: B (-nn)**
   * *Explanation:* The -nn flag forces tcpdump to display raw numeric IP addresses and port numbers, disabling slow reverse DNS pointer lookups and service name translations.
 4. **Correct Answer: B (By inspecting log files or systemd journals for repeated authentication failure patterns using regex filters)**
   * *Explanation:* Fail2ban monitors log streams (such as /var/log/auth.log or the systemd journal) for login failure patterns. When threshold limits defined in jail.local are breached, it issues commands to insert drop rules into nftables or iptables.

 * B) By inspecting log files or systemd journals for repeated authentication failure patterns using regex filters.
 * C) By querying external threat intelligence public blocklists over encrypted HTTPS APIs.
 * D) By executing continuous AIDE cryptographic checksum checks on the /etc/passwd file.
### Answers and Explanations
 1. **Correct Answer: C (PREROUTING)**
   * *Explanation:* The PREROUTING hook intercepts packets as soon as they enter the network stack, before the routing subsystem decides whether the packet is intended for the local host (INPUT) or needs to be routed elsewhere (FORWARD).
 2. **Correct Answer: C (ESTABLISHED)**
   * *Explanation:* The ESTABLISHED state matches packets that are part of an already negotiated, bidirectional connection track.
 3. **Correct Answer: B (-nn)**
   * *Explanation:* The -nn flag forces tcpdump to display raw numeric IP addresses and port numbers, disabling slow reverse DNS pointer lookups and service name translations.
 4. **Correct Answer: B (By inspecting log files or systemd journals for repeated authentication failure patterns using regex filters)**
   * *Explanation:* Fail2ban monitors log streams (such as /var/log/auth.log or the systemd journal) for login failure patterns. When threshold limits defined in jail.local are breached, it issues commands to insert drop rules into nftables or iptables.
